# HyperShift GMP-Native Monitoring Resource Support

***Scope***: GCP-HCP

**Date**: 2026-09-23

**Status**: Proposed — pending HyperShift team review and sign-off

**Jira**: [GCP-1227](https://redhat.atlassian.net/browse/GCP-1227) (Story) under [GCP-423](https://redhat.atlassian.net/browse/GCP-423) (Epic)

## Decision

We will add a monitoring API-group **selection** to HyperShift so that the control-plane-operator (CPOv2) and the `hypershift install` command can emit Google Managed Prometheus (GMP) resources (`monitoring.googleapis.com`: `PodMonitoring`, `Rules`) as an alternative to the existing CoreOS Prometheus Operator resources (`monitoring.coreos.com`: `ServiceMonitor`, `PodMonitor`, `PrometheusRule`). The proposed activation interface is a **`MONITORING_API_GROUP` environment variable** on both binaries, defaulting to `monitoring.coreos.com`, with `monitoring.googleapis.com` as the second valid value. An environment variable is used — rather than a CLI flag — because the `hypershift install` binary itself emits monitoring resources using a runtime scheme that is initialized at `init()` time, *before* CLI flags are parsed; an env var is readable at that point, matching the existing `RHOBS_MONITORING` mechanism. GMP resources are authored as **separate, hand-maintained manifests/constructors** (not generated by converting CoreOS manifests at runtime). Setting the variable together with the existing `RHOBS_MONITORING=1` mechanism is a fatal startup error. No `HostedCluster` API field is added.



## Context

This decision **evolves** the earlier [Observability Platform: Google Managed Prometheus](observability-google-managed-prometheus.md) decision. That decision deliberately chose a *hybrid* model — a self-managed Prometheus per management cluster that scrapes the CoreOS monitors and remote-writes filtered metrics to GMP — precisely because native GMP `PodMonitoring` "requires rewrite of HyperShift monitoring templates." GCP-423/GCP-1227 is the decision to now do that rewrite so the dedicated Prometheus (added in [gcp-hcp-infra #337](https://github.com/openshift-online/gcp-hcp-infra/pull/337)) can be removed, eliminating per-cluster Prometheus overhead and aligning with GKE-native observability.

### Problem Statement

GKE management clusters already run GMP collectors in `gke-gmp-system` that natively scrape `monitoring.googleapis.com` CRDs but cannot read `monitoring.coreos.com` CRDs. HyperShift emits only CoreOS monitors, so GCP HCP must deploy a dedicated self-managed Prometheus in every management cluster as a translation shim. To decommission that Prometheus, HyperShift must be able to emit GMP-native monitoring resources for the same targets — without regressing the existing CoreOS behavior that self-managed HyperShift, ROSA HCP, and ARO HCP depend on.

### Constraints

- **No regression for existing consumers**: The default (no flag) and the existing `RHOBS_MONITORING=1` path must be byte-for-byte unchanged. ROSA HCP and ARO HCP must be unaffected.
- **This is an upstream HyperShift change**: Code lands in `github.com/openshift/hypershift` and must be acceptable to its maintainers. It cannot depend on GCP-only assumptions leaking into shared code paths.
- **Scheme registration timing**: Monitoring Go types are registered into the runtime scheme in `support/api/scheme.go` at `init()` time based on `os.Getenv("RHOBS_MONITORING")` — *before* CLI flags are parsed (`scheme.go:101-148`), and the `hypershift install` binary emits monitoring resources using that already-initialized scheme. This ordering is precisely why RHOBS is an env var and not a flag, and it is why this decision selects an env var (`MONITORING_API_GROUP`) too: the value is available at `init()`, before the scheme and the install-time emitters are built, so no restructuring of scheme initialization is required. (A CLI flag would arrive after the scheme is already initialized and would require reworking that init path — see Alternatives.) Registering a type is *inert* — it only teaches the client/serializer to (de)serialize that Kind; it creates, lists, and watches nothing. The existing `AllMonitoringScheme` (`scheme.go:74,106-107`, backing `AllMonitoringYamlSerializer`) is precedent for holding more than one monitoring group in one scheme (today `monitoring.coreos.com` + `monitoring.rhobs`), but it is a *decode helper*, not the isolation mechanism.
- **Existing-platform isolation (ROSA/ARO/self-managed)**: Isolation of the existing platforms comes from the **env-var default (`monitoring.coreos.com`) plus the `isGMP` predicate**, not from scheme contents. Management clusters serving self-managed HyperShift, ROSA HCP, and ARO HCP never set the variable to GMP, so `isGMP` is false and no GMP resource is ever constructed or applied there — regardless of which types happen to be registered. The change must not alter the coreos/rhobs registration those platforms already build.
- **No `HostedCluster` API change**: Selection must be a binary/install concern, not a customer-facing spec field, to avoid an API review cycle and to keep the choice an operational property of the management cluster.
- **GMP CRD Go types are not vendored** (build-time concern, distinct from runtime CRD availability): The `monitoring.googleapis.com` CRDs are already installed on GKE management clusters (`gke-gmp-system`), and gcp-hcp already applies `PodMonitoring` resources as plain YAML (e.g. for ArgoCD) — that path needs no Go dependency. However, HyperShift builds its monitors as *typed Go objects* (the CoreOS `prometheus-operator` types are vendored and used by CPOv2 adapt functions and the `hypershift install` constructors), so emitting GMP resources the same way requires vendoring the GMP Go structs (e.g. `github.com/GoogleCloudPlatform/prometheus-engine`). The alternative — emitting GMP resources as `unstructured.Unstructured`/verbatim YAML to avoid the dependency, at the cost of compile-time typing — is discussed in the implementation plan.
  - *Why the RHOBS "just change registration" trick does not transfer*: `RHOBS_MONITORING` needs no new vendoring because `monitoring.rhobs` is **schema-identical** to `monitoring.coreos.com` — it reuses the *same* `prometheus-operator` Go structs (`ServiceMonitor`/`PodMonitor`/`PrometheusRule`) under a different GroupVersion, so re-registering the existing types produces valid output. GMP is **not** a renamed CoreOS schema: it has different Kinds (`PodMonitoring`/`Rules`), pod-based `spec.endpoints[]` instead of Service-based selection, `tls` vs `tlsConfig`, Secret-only CA refs, etc. Re-registering the CoreOS structs under the `monitoring.googleapis.com` group would serialize CoreOS fields under a GMP `apiVersion`, which the `gke-gmp-system` collectors cannot consume. Emitting *valid* GMP therefore requires either vendoring the GMP structs or building the resources as `unstructured` — the scheme-registration approach alone does not avoid this (see Open Question #4).
- **Auth/discovery differences**: GMP `PodMonitoring` discovers pods directly (not via Services) and models TLS/auth differently from CoreOS monitors. Sensitive targets (etcd mTLS, kube-apiserver bearer token) need explicit validation.
- **The CoreOS→GMP mapping is not 1:1**: GMP has **no Service-based monitor** — only `PodMonitoring` (namespace-scoped) and `ClusterPodMonitoring` (cluster-wide), both pod-based. Both CoreOS kinds (`ServiceMonitor` *and* `PodMonitor`) therefore collapse onto `PodMonitoring`, and a `ServiceMonitor`'s Service→endpoints discovery must be re-expressed as a pod label selector that reproduces the same target set (Google's own docs note the ServiceMonitor→PodMonitoring field mapping is *incomplete*). Because `PodMonitoring.spec.endpoints` is a list, multiple CoreOS monitors that target the same pods may be **consolidated** into a single `PodMonitoring` with several endpoints. Consequently parity cannot be defined as a per-file or per-kind "twin"; it must be defined as **scrape-target coverage** — every (component, port, metrics path, MetricSet) a CoreOS monitor scrapes must be covered by some GMP endpoint (see the implementation plan's parity test and Open Question #3).

### Assumptions

- The metric keep/drop lists encoded in `support/metrics/sets.go` are portable to GMP (standard PromQL regex on `__name__`); only the surrounding relabel *type* differs.



## Alternatives Considered

The core open question is the **activation interface**. Four options were weighed; the GMP-manifest-authoring approach (separate files vs. runtime conversion) is treated as a secondary decision below.

1. **Environment variable `MONITORING_API_GROUP` on both binaries** *(proposed)*: A variable read at `init()` with validated enum values (`monitoring.coreos.com` default, `monitoring.googleapis.com`), mirroring how `RHOBS_MONITORING` swaps the scheme today (`support/api/scheme.go:141-148`, `support/rhobsmonitoring/scheme.go`). Zero flag-parsing/ordering concerns because it is available before scheme registration and before the `hypershift install` emitters run, and consistent with the existing precedent the maintainers already use for monitoring-backend selection. The trade-off is that env-var configuration is less discoverable than a flag and must be set consistently across the two binaries. Unlike the RHOBS precedent — which pairs its env var with a `--rhobs-monitoring` flag used only to validate consistency — selection here is env-var-only; no analogous validation flag is proposed (it can be added later if maintainers want the cross-check). Note the `RHOBS_MONITORING` env var is an existing, still-in-use mechanism in the HyperShift repo; GCP HCP does not use it, and this decision leaves it untouched.
2. **CLI flag `--monitoring-api-group` on both binaries**: A string flag with the same validated enum values. More explicit, discoverable via `--help`, and self-documenting in Deployment manifests. Rejected as the activation interface because the `hypershift install` binary emits monitoring resources using a scheme initialized at `init()` — before flags are parsed — so a flag value arrives too late to select the scheme without reworking how the CLI initializes it. HyperShift maintainer review of this decision confirmed the env var is the preferred mechanism for exactly this reason.
3. **`HostedCluster` API field**: A spec field selecting the monitoring backend per hosted cluster. Most explicit and per-cluster granular, but requires an upstream API review, adds a customer-facing surface for what is really a management-cluster property, and is rejected by the ticket scope.
4. **Runtime conversion of CoreOS manifests to GMP**: Keep single-source CoreOS manifests and generate GMP resources on the fly via a conversion function. Avoids duplicated manifests, but creates fragile coupling where an innocuous CoreOS change silently produces invalid GMP output, and hides the real schema differences (Service- vs pod-based discovery, `tlsConfig`→`tls`, ConfigMap-CA→Secret-CA). Rejected for the *authoring* dimension regardless of the activation interface chosen.

## Decision Rationale

* **Justification (activation interface)**: An environment variable (`MONITORING_API_GROUP`) is selected because the `hypershift install` binary emits monitoring resources using a runtime scheme initialized at `init()`, before CLI flags are parsed. An env var is available at that point, so the selection can take effect without reworking how the CLI initializes its scheme — the same reason `RHOBS_MONITORING` is an env var rather than a flag. It still composes cleanly with startup validation (reject `MONITORING_API_GROUP=monitoring.googleapis.com` + `RHOBS_MONITORING=1` with an actionable error) and with focused unit tests. Emission is gated by the env-var default (`monitoring.coreos.com`) plus the `isGMP` predicate, so a management cluster that never sets the variable (self-managed, ROSA, ARO) is behaviorally unchanged whatever types are registered. The approach leaves the existing `RHOBS_MONITORING` `init()` path (still in use, though not by GCP HCP) untouched. **This reasoning reflects HyperShift maintainer feedback, which favored the env var over a CLI flag for exactly this ordering reason; it is presented for continued maintainer validation, not as a settled cross-team mandate.**
* **Justification (separate manifests)**: Authoring GMP resources as distinct assets/constructors, gated by the existing CPOv2 predicate system (`component.WithManifestAdapter(...).WithPredicate(isGMP)`), reuses a proven pattern — the same one used for ARO-only assets such as `config-secretprovider.yaml` gated behind `isAroHCP` (`v2/cloud_controller_manager/azure/component.go:55-57`). It keeps CoreOS and GMP manifests independently reviewable and makes discovery/TLS/auth differences explicit rather than emergent.
* **Evidence**: The CPOv2 component framework already supports per-manifest predicates and adapt functions (`support/controlplane-component/builder.go:69-90`) and multi-file component directories via `//go:embed */*.yaml` (`v2/assets/assets.go:20`), so no framework changes are required. MetricSet filtering is centralized in reusable functions returning `[]prometheusoperatorv1.RelabelConfig` (`support/metrics/sets.go`: `EtcdRelabelConfigs` at 139, `KASRelabelConfigs` at 157), so GMP adapters can call the same functions and translate the output — no duplication of allow/drop lists. The RHOBS precedent is instructive on the interface: selection is driven by the `RHOBS_MONITORING` env var at `init()`, and the `--rhobs-monitoring` flag exists only to *validate consistency against* that env var (`cmd/install/install.go:345-346`) — not to drive the scheme. This mirrors the env-var-first approach chosen here.
* **Comparison**: The CLI flag (2) is more discoverable but arrives after the install-time scheme is already initialized, so it cannot drive selection without reworking CLI scheme init — the reason it is rejected as the activation interface. The API field (3) is over-scoped for a management-cluster property and triggers an API review. Runtime conversion (4) optimizes for fewer files at the cost of exactly the correctness guarantees (parity, explicit auth translation) this work most needs.

## Consequences

### Positive

* GKE management clusters can scrape hosted control plane and management-level metrics natively via GMP collectors — no per-cluster self-managed Prometheus.
* Default and `RHOBS_MONITORING=1` behavior is untouched; ROSA HCP and ARO HCP are unaffected.
* GMP and CoreOS manifests are independently reviewable; schema/auth differences are explicit, not hidden in a converter.
* A repository-level parity test makes it impossible to add a CoreOS monitor without a GMP equivalent (or an explicit waiver), preventing silent coverage gaps.
* Reuses existing MetricSet relabel logic, preserving Telemetry/SRE/All semantics with no duplicated allow/drop lists.
* Leaves the `RHOBS_MONITORING` path fully untouched — it stays in use for those who rely on it; this design neither depends on nor changes it.

### Negative

* Adds a second, hand-maintained set of monitoring manifests covering all current scrape targets (11 ServiceMonitors + 8 PodMonitors + 1 PrometheusRule at CPO level, plus 4 management-level monitors). Because the mapping is not 1:1 — `ServiceMonitor`/`PodMonitor` both collapse to `PodMonitoring` and same-pod targets may be consolidated into one `PodMonitoring` with multiple endpoints — the GMP side is likely *fewer* files than the CoreOS side, but it remains a parallel surface to keep in sync. Mitigated by the coverage-based parity test and shared relabel logic.
* Adds a new build/vendor dependency for `monitoring.googleapis.com` CRD Go types.
* ServiceMonitor→PodMonitoring is not a mechanical swap: Service-based discovery, port naming, and (for etcd/kube-apiserver) mTLS/bearer-token auth must be re-expressed and validated per target. If GMP collectors cannot present etcd client certificates, etcd scraping is blocked and needs a different approach — this is the primary implementation risk and must be spiked first.
* NetworkPolicy must be widened, only on the GMP path, to admit `gke-gmp-system` collectors; getting the selector wrong either blocks scraping or over-exposes control plane pods.
* GMP evaluates `Rules` via a managed in-cluster `rule-evaluator` (deployed in `gke-gmp-system`) that **queries the Monarch backend** for the underlying time series, rather than a self-managed in-cluster Prometheus that both stores and evaluates. Evaluating against a remote backend (rather than local TSDB) may change alert timing/semantics versus locally-evaluated `PrometheusRule`s.

## Cross-Cutting Concerns

### Reliability

* **Scalability**: Native GMP collection removes the self-managed Prometheus as a per-management-cluster scaling bottleneck and shifts time-series *storage* to Google-managed Monarch (rule evaluation stays in-cluster via the managed `rule-evaluator`, which queries that backend). Metric volume moves directly into Cloud Monitoring ingestion quotas — sizing and cost are owned by the follow-up ops story.
* **Observability**: The change is to the monitoring plumbing itself; success is measured by GMP scrape coverage/parity against the current Prometheus target set (validated in the follow-up story). A parity unit/repo test guards code-level coverage.
* **Resiliency**: Evaluating rules against the Monarch backend (via the managed `rule-evaluator`) means recording/alerting rules survive management-cluster-local Prometheus failures (there is no such Prometheus on the GMP path), but introduces dependence on GMP backend availability and query/evaluation latency.

### Security

* Preserves TLS and authentication semantics for sensitive targets. etcd requires mTLS with client certificates; kube-apiserver uses a bearer token. GMP models TLS differently (`tls` vs `tlsConfig`, `key`/`cert`/`ca` as Secret references, no ConfigMap-CA support), so each sensitive target's auth must be re-expressed and verified rather than assumed equivalent.
* NetworkPolicy is widened **only** when GMP is selected, using stable `gke-gmp-system` namespace/pod selectors; the default, ROSA HCP, and ARO HCP policies are unchanged (`reconcileOpenshiftMonitoringNetworkPolicy`, `network_policies.go:576-593`). This reconciler runs in the **hypershift-operator** — a third binary distinct from the two that *emit* monitors — so it must read the same `MONITORING_API_GROUP` selection independently to know when to widen the policy (plumbing detailed in the implementation plan).
* Startup validation fails fast if `MONITORING_API_GROUP=monitoring.googleapis.com` and `RHOBS_MONITORING=1` are combined, preventing an ambiguous/insecure mixed configuration.

### Cost

* Native GMP ingestion is billed per sample in Cloud Monitoring; removing the self-managed Prometheus removes its compute/storage footprint but exposes raw ingestion volume to GMP quotas. Aggressive MetricSet filtering (Telemetry/SRE) remains the primary cost lever and is preserved by reusing the existing relabel functions. Quantified cost/quota analysis is explicitly deferred to the follow-up ops story (see the [hybrid GMP cost analysis](observability-google-managed-prometheus.md#cost) for the current baseline).

### Operability

* Selection is visible in the rendered Deployment (the env var appears in the container spec), aiding debugging and drift detection.
* Cutover is staged: this story ships the *capability* (dark by default); a follow-up ops story enables GMP on GKE management clusters, validates live scrape/parity, and removes the dedicated Prometheus from gcp-hcp-infra.
* HyperShift repository documentation must be updated to cover installing the GMP CRDs and using the new `MONITORING_API_GROUP` env var (tracked as documentation tasks under GCP-1227).

## Open Questions for HyperShift Team Review

These require HyperShift maintainer sign-off before implementation:

1. **Activation interface — variable name and accepted values**: The *mechanism* is settled (an environment variable consistent with `RHOBS_MONITORING`, not a CLI flag — see the Decision and Rationale above, confirmed by HyperShift maintainer review, since `hypershift install` emits monitoring resources from a scheme initialized before CLI flags are parsed). What remains open is confirmation of the concrete surface: is `MONITORING_API_GROUP` the name the maintainers want, and are `monitoring.coreos.com` (default) / `monitoring.googleapis.com` the accepted values? The names used throughout this document are proposed, not final.
2. **Scheme registration**: For adding the GMP types at `init()` (driven by the env var), does the team prefer **additive** registration (simplest; inert for other platforms) or **register-on-demand** based on the env-var value (leaves the coreos/rhobs scheme byte-identical for ROSA/ARO/self-managed)? Either must avoid touching the existing coreos/rhobs registration.
3. **Parity enforcement**: Because the CoreOS→GMP mapping is not 1:1 (no ServiceMonitor kind; `ServiceMonitor`/`PodMonitor` both collapse to `PodMonitoring`; monitors may be consolidated into one `PodMonitoring` with multiple endpoints), parity is defined as **scrape-target coverage** rather than a per-file twin: a repo-level Go test extracts the scrape targets from all CoreOS monitors and asserts each is covered by some GMP endpoint. Is that coverage-based guard the right approach, and where should it live?
4. **CRD dependency**: Which GMP CRD Go module/version should be vendored (e.g. `github.com/GoogleCloudPlatform/prometheus-engine`), and any concerns about adding it to the HyperShift module?
