# HyperShift GMP-Native Monitoring Resource Support

***Scope***: GCP-HCP

**Date**: 2026-09-23

**Status**: Proposed — pending HyperShift team review and sign-off 

**Jira**: [GCP-1227](https://redhat.atlassian.net/browse/GCP-1227) (Story) under [GCP-423](https://redhat.atlassian.net/browse/GCP-423) (Epic)

## Decision

We will add a monitoring API-group **selection** to HyperShift so that the control-plane-operator (CPOv2) and the `hypershift install` command can emit Google Managed Prometheus (GMP) resources (`monitoring.googleapis.com`: `PodMonitoring`, `Rules`) as an alternative to the existing CoreOS Prometheus Operator resources (`monitoring.coreos.com`: `ServiceMonitor`, `PodMonitor`, `PrometheusRule`). The proposed activation interface is a **`--monitoring-api-group` CLI flag** on both binaries, defaulting to `monitoring.coreos.com`, with `monitoring.googleapis.com` as the second valid value. GMP resources are authored as **separate, hand-maintained manifests/constructors** (not generated by converting CoreOS manifests at runtime). Setting the flag together with the existing `RHOBS_MONITORING=1` mechanism is a fatal startup error. No `HostedCluster` API field is added.



## Context

This decision **evolves** the earlier [Observability Platform: Google Managed Prometheus](observability-google-managed-prometheus.md) decision. That decision deliberately chose a *hybrid* model — a self-managed Prometheus per management cluster that scrapes the CoreOS monitors and remote-writes filtered metrics to GMP — precisely because native GMP `PodMonitoring` "requires rewrite of HyperShift monitoring templates." GCP-423/GCP-1227 is the decision to now do that rewrite so the dedicated Prometheus (added in [gcp-hcp-infra #337](https://github.com/openshift-online/gcp-hcp-infra/pull/337)) can be removed, eliminating per-cluster Prometheus overhead and aligning with GKE-native observability.

### Problem Statement

GKE management clusters already run GMP collectors in `gke-gmp-system` that natively scrape `monitoring.googleapis.com` CRDs but cannot read `monitoring.coreos.com` CRDs. HyperShift emits only CoreOS monitors, so GCP HCP must deploy a dedicated self-managed Prometheus in every management cluster as a translation shim. To decommission that Prometheus, HyperShift must be able to emit GMP-native monitoring resources for the same targets — without regressing the existing CoreOS behavior that self-managed HyperShift, ROSA HCP, and ARO HCP depend on.

### Constraints

- **No regression for existing consumers**: The default (no flag) and the existing `RHOBS_MONITORING=1` path must be byte-for-byte unchanged. ROSA HCP and ARO HCP must be unaffected.
- **This is an upstream HyperShift change**: Code lands in `github.com/openshift/hypershift` and must be acceptable to its maintainers. It cannot depend on GCP-only assumptions leaking into shared code paths.
- **Scheme registration timing**: Monitoring Go types are registered into the runtime scheme in `support/api/scheme.go` at `init()` time based on `os.Getenv("RHOBS_MONITORING")` — *before* CLI flags are parsed (`scheme.go:101-148`). This ordering is precisely why RHOBS is an env var and not a flag. A flag-driven selection must therefore register the GMP types either **additively** or **on-demand after flag parse** (see Rationale). Registering a type is *inert* — it only teaches the client/serializer to (de)serialize that Kind; it creates, lists, and watches nothing. The existing `AllMonitoringScheme` (`scheme.go:74,106-107`, backing `AllMonitoringYamlSerializer`) is precedent for holding more than one monitoring group in one scheme (today `monitoring.coreos.com` + `monitoring.rhobs`), but it is a *decode helper*, not the isolation mechanism.
- **Existing-platform isolation (ROSA/ARO/self-managed)**: Isolation of the existing platforms comes from the **flag default (`monitoring.coreos.com`) plus the `isGMP` predicate**, not from scheme contents. Management clusters serving self-managed HyperShift, ROSA HCP, and ARO HCP never set the flag to GMP, so `isGMP` is false and no GMP resource is ever constructed or applied there — regardless of which types happen to be registered. The change must not alter the coreos/rhobs registration those platforms already build.
- **No `HostedCluster` API change**: Selection must be a binary/install concern, not a customer-facing spec field, to avoid an API review cycle and to keep the choice an operational property of the management cluster.
- **GMP CRD Go types are not vendored** (build-time concern, distinct from runtime CRD availability): The `monitoring.googleapis.com` CRDs are already installed on GKE management clusters (`gke-gmp-system`), and gcp-hcp already applies `PodMonitoring` resources as plain YAML (e.g. for ArgoCD) — that path needs no Go dependency. However, HyperShift builds its monitors as *typed Go objects* (the CoreOS `prometheus-operator` types are vendored and used by CPOv2 adapt functions and the `hypershift install` constructors), so emitting GMP resources the same way requires vendoring the GMP Go structs (e.g. `github.com/GoogleCloudPlatform/prometheus-engine`). The alternative — emitting GMP resources as `unstructured.Unstructured`/verbatim YAML to avoid the dependency, at the cost of compile-time typing — is discussed in the implementation plan.
- **Auth/discovery differences**: GMP `PodMonitoring` discovers pods directly (not via Services) and models TLS/auth differently from CoreOS monitors. Sensitive targets (etcd mTLS, kube-apiserver bearer token) need explicit validation.

### Assumptions

- The metric keep/drop lists encoded in `support/metrics/sets.go` are portable to GMP (standard PromQL regex on `__name__`); only the surrounding relabel *type* differs.



## Alternatives Considered

The core open question is the **activation interface**. Four options were weighed; the GMP-manifest-authoring approach (separate files vs. runtime conversion) is treated as a secondary decision below.

1. **CLI flag `--monitoring-api-group` on both binaries** *(proposed)*: A string flag with validated enum values (`monitoring.coreos.com` default, `monitoring.googleapis.com`). Explicit, discoverable via `--help`, testable, and self-documenting in Deployment manifests. Requires decoupling scheme registration from selection by registering the GMP types additively or on-demand after flag parse, without altering the existing coreos/rhobs registration.
2. **Environment variable (the `RHOBS_MONITORING` pattern)**: Add e.g. `MONITORING_API_GROUP` read at `init()`, mirroring how `RHOBS_MONITORING` swaps the scheme today (`support/api/scheme.go:141-148`, `support/rhobsmonitoring/scheme.go`). Zero flag-parsing/ordering concerns because it is available before scheme registration, and consistent with the existing precedent — but env-var configuration is less discoverable and easy to set inconsistently across the two binaries. Note the `RHOBS_MONITORING` env var is an existing, still-in-use mechanism in the HyperShift repo; GCP HCP does not use it, and this decision leaves it untouched.
3. **`HostedCluster` API field**: A spec field selecting the monitoring backend per hosted cluster. Most explicit and per-cluster granular, but requires an upstream API review, adds a customer-facing surface for what is really a management-cluster property, and is rejected by the ticket scope.
4. **Runtime conversion of CoreOS manifests to GMP**: Keep single-source CoreOS manifests and generate GMP resources on the fly via a conversion function. Avoids duplicated manifests, but creates fragile coupling where an innocuous CoreOS change silently produces invalid GMP output, and hides the real schema differences (Service- vs pod-based discovery, `tlsConfig`→`tls`, ConfigMap-CA→Secret-CA). Rejected for the *authoring* dimension regardless of the activation interface chosen.

## Decision Rationale

* **Justification (activation interface)**: A CLI flag makes the monitoring backend an explicit, validated, discoverable property of each binary invocation and of the rendered Deployment spec, which matters when a HyperShift operator instance and its CPOs must agree. It composes cleanly with startup validation (reject `--monitoring-api-group` + `RHOBS_MONITORING=1` with an actionable error) and with focused unit tests. The one real cost — that scheme registration precedes flag parsing — is handled by registering the GMP types **additively** (registration is inert) or **on-demand** after the flag is parsed and before the manager is built, *never* by altering the coreos/rhobs registration that ROSA HCP and ARO HCP rely on. Emission is gated by the flag default (`monitoring.coreos.com`) plus the `isGMP` predicate, so a management cluster that never sets the flag (self-managed, ROSA, ARO) is behaviorally unchanged whatever types are registered. This is a lighter lift than the env-var path implies, and it leaves the existing `RHOBS_MONITORING` `init()` path (still in use, though not by GCP HCP) untouched. **This reasoning is presented for HyperShift maintainer validation, not as a settled cross-team mandate.**
* **Justification (separate manifests)**: Authoring GMP resources as distinct assets/constructors, gated by the existing CPOv2 predicate system (`component.WithManifestAdapter(...).WithPredicate(isGMP)`), reuses a proven pattern — the same one used for ARO-only assets such as `config-secretprovider.yaml` gated behind `isAroHCP` (`v2/cloud_controller_manager/azure/component.go:55-57`). It keeps CoreOS and GMP manifests independently reviewable and makes discovery/TLS/auth differences explicit rather than emergent.
* **Evidence**: The CPOv2 component framework already supports per-manifest predicates and adapt functions (`support/controlplane-component/builder.go:69-90`) and multi-file component directories via `//go:embed */*.yaml` (`v2/assets/assets.go:20`), so no framework changes are required. MetricSet filtering is centralized in reusable functions returning `[]prometheusoperatorv1.RelabelConfig` (`support/metrics/sets.go`: `EtcdRelabelConfigs` at 139, `KASRelabelConfigs` at 157), so GMP adapters can call the same functions and translate the output — no duplication of allow/drop lists. The RHOBS precedent (`--rhobs-monitoring` flag validated against the env var in `cmd/install/install.go:345-346`) demonstrates the team already models monitoring-backend selection at the CLI layer.
* **Comparison**: The env var (2) is the most consistent with existing code but follows the `init()` env-var pattern and is the least discoverable. The API field (3) is over-scoped for a management-cluster property and triggers an API review. Runtime conversion (4) optimizes for fewer files at the cost of exactly the correctness guarantees (parity, explicit auth translation) this work most needs.

## Consequences

### Positive

* GKE management clusters can scrape hosted control plane and management-level metrics natively via GMP collectors — no per-cluster self-managed Prometheus.
* Default and `RHOBS_MONITORING=1` behavior is untouched; ROSA HCP and ARO HCP are unaffected.
* GMP and CoreOS manifests are independently reviewable; schema/auth differences are explicit, not hidden in a converter.
* A repository-level parity test makes it impossible to add a CoreOS monitor without a GMP equivalent (or an explicit waiver), preventing silent coverage gaps.
* Reuses existing MetricSet relabel logic, preserving Telemetry/SRE/All semantics with no duplicated allow/drop lists.
* Leaves the `RHOBS_MONITORING` path fully untouched — it stays in use for those who rely on it; this design neither depends on nor changes it.

### Negative

* Roughly doubles the number of maintained monitoring manifests (a GMP twin for each of 11 ServiceMonitors + 8 PodMonitors + 1 PrometheusRule at CPO level, plus 4 management-level monitors) — mitigated by the parity test and shared relabel logic.
* Adds a new build/vendor dependency for `monitoring.googleapis.com` CRD Go types.
* ServiceMonitor→PodMonitoring is not a mechanical swap: Service-based discovery, port naming, and (for etcd/kube-apiserver) mTLS/bearer-token auth must be re-expressed and validated per target. If GMP collectors cannot present etcd client certificates, etcd scraping is blocked and needs a different approach — this is the primary implementation risk and must be spiked first.
* NetworkPolicy must be widened, only on the GMP path, to admit `gke-gmp-system` collectors; getting the selector wrong either blocks scraping or over-exposes control plane pods.
* GMP evaluates `Rules` remotely (in Monarch) rather than in-cluster, which may change alert timing/semantics versus locally-evaluated `PrometheusRule`s.

## Cross-Cutting Concerns

### Reliability

* **Scalability**: Native GMP collection removes the self-managed Prometheus as a per-management-cluster scaling bottleneck and shifts storage/evaluation to Google-managed Monarch. Metric volume moves directly into Cloud Monitoring ingestion quotas — sizing and cost are owned by the follow-up ops story.
* **Observability**: The change is to the monitoring plumbing itself; success is measured by GMP scrape coverage/parity against the current Prometheus target set (validated in the follow-up story). A parity unit/repo test guards code-level coverage.
* **Resiliency**: Remote rule evaluation means recording/alerting rules survive management-cluster-local Prometheus failures (there is no such Prometheus on the GMP path), but introduces dependence on GMP backend availability and evaluation latency.

### Security

* Preserves TLS and authentication semantics for sensitive targets. etcd requires mTLS with client certificates; kube-apiserver uses a bearer token. GMP models TLS differently (`tls` vs `tlsConfig`, `key`/`cert`/`ca` as Secret references, no ConfigMap-CA support), so each sensitive target's auth must be re-expressed and verified rather than assumed equivalent.
* NetworkPolicy is widened **only** when GMP is selected, using stable `gke-gmp-system` namespace/pod selectors; the default, ROSA HCP, and ARO HCP policies are unchanged (`reconcileOpenshiftMonitoringNetworkPolicy`, `network_policies.go:576-593`).
* Startup validation fails fast if `--monitoring-api-group` and `RHOBS_MONITORING=1` are combined, preventing an ambiguous/insecure mixed configuration.

### Cost

* Native GMP ingestion is billed per sample in Cloud Monitoring; removing the self-managed Prometheus removes its compute/storage footprint but exposes raw ingestion volume to GMP quotas. Aggressive MetricSet filtering (Telemetry/SRE) remains the primary cost lever and is preserved by reusing the existing relabel functions. Quantified cost/quota analysis is explicitly deferred to the follow-up ops story (see the [hybrid GMP cost analysis](observability-google-managed-prometheus.md#cost) for the current baseline).

### Operability

* Selection is visible in the rendered Deployment/command line, aiding debugging and drift detection.
* Cutover is staged: this story ships the *capability* (dark by default); a follow-up ops story enables GMP on GKE management clusters, validates live scrape/parity, and removes the dedicated Prometheus from gcp-hcp-infra.
* HyperShift repository documentation must be updated to cover installing the GMP CRDs and using the new flag (tracked as documentation tasks under GCP-1227).

## Open Questions for HyperShift Team Review

These require HyperShift maintainer sign-off before implementation:

1. **Activation interface**: Is a `--monitoring-api-group` CLI flag on both binaries the interface the maintainers want, versus an environment variable consistent with `RHOBS_MONITORING`, or another mechanism? (Primary decision.)
2. **Scheme registration**: For adding the GMP types, does the team prefer **additive** registration (simplest; inert for other platforms) or **register-on-demand** after flag parse (leaves the coreos/rhobs scheme byte-identical for ROSA/ARO/self-managed)? Either must avoid touching the existing coreos/rhobs registration.
3. **Parity enforcement**: Is a repo-level Go test that fails when a CoreOS monitor lacks a GMP twin the right guard, and where should it live?
4. **CRD dependency**: Which GMP CRD Go module/version should be vendored (e.g. `github.com/GoogleCloudPlatform/prometheus-engine`), and any concerns about adding it to the HyperShift module?
