### Signature/trust results

Used Red Hat's documented [container signature policy](https://access.redhat.com/articles/3116561) and [published product signing keys](https://access.redhat.com/security/team/key): GPG simple signing, Red Hat release key 2 fingerprint `567E347AD0044ADE55BA8A5F199E2F91FD431D51`, key fetched from its official linked [endpoint](https://security.access.redhat.com/data/fd431d51.txt), signatures from `https://registry.redhat.io/containers/sigstore`.

**Observed:** all 15 distinct related-image index manifests plus the bundle manifest matched their requested SHA-256 digest and passed `skopeo standalone-verify` with that exact key, exact manifest bytes and same-repository signed identity. The bundle manifest and its detached signature are retained at the evidence root for the offline check; the 16 per-image manifest and signature pairs are re-fetched from `registry.redhat.io` when re-verifying. The bundle additionally passed a full `skopeo copy --preserve-digests` under isolated policy with default `reject`, registry-scoped `signedBy`, and `signedIdentity=matchRepoDigestOrExact`. An altered-manifest negative test failed with digest mismatch. See [review-summary.json](gcp-1286-evidence/review-summary.json) for `bundleFullPolicyCopyVerified` and `tamperedManifestRejected`.

The signed identity uses a tag (for example `gitops-operator-bundle:1.22`). Exact string comparison against an `@sha256:` reference initially failed, as expected. The final verification binds the signature to the immutable manifest digest and repository; it does not resolve the mutable tag. This is the documented [containers/image digest-reference identity behavior](https://github.com/containers/image/blob/main/docs/containers-policy.json.5.md), not an insecure-policy exception.

Limits: the 2026-11-10 fresh copies covered the bundle and the four required images for linux/amd64 and linux/arm64/v8. Each copy ran under the fail-closed policy, so the signed index was enforced, and every config and layer blob those selected manifests reference was downloaded and hash-verified ([results](gcp-1286-evidence/fresh-copies/)). ppc64le/s390x and other image references were not fetched, and separate platform-child signatures were not tested. Release-key-3 Sigstore signatures **were** verified on 2026-11-11 for the bundle and the four required images: every `registry.redhat.io` signature in each `sha256-<digest>.sig` artifact verifies and binds the approved digest, signed by release key 3 (`E60D446E63405576`). Whether key 3 is *required* remains a Product Security policy question (B3); the evidence now exists either way ([results](gcp-1286-evidence/sigstore/)). No chart signature was verified: #166's charts are local artifacts. No GKE node admission or runtime signature enforcement is claimed, and GKE has no CRI-O `ClusterImagePolicy` to enforce it at pull time.

This is a release-branch trace, not an assumption that master ancestry proves inclusion. Both runtime topologies still require tests.

**Runtime observation 2026-11-13 (MC):** the manager registers the Route type only at startup. On the disposable MC the manager started at `16:00:03Z`, HyperShift's Route CRD arrived through the application sync at `16:47:00Z`, and the manager then failed every route reconcile with `no kind is registered for the type v1.Route` until it was restarted at `17:08Z`. The 1.22.2 backport fixes Route-without-Config detection at startup; it does not cover a Route API that appears after startup. On an MC that installs HyperShift through GitOps, manager-first is the normal order. This needs an upstream issue or a documented restart/order step; details in [`gitops-release-validation/2026-11-13-dev-pair.md`](gitops-release-validation/2026-11-13-dev-pair.md) §5.3.
