## 5. Findings

### 5.1 ApplicationSet controller RBAC (fixed in the bundle)

Symptom: `ArgoCD/gitops` stayed `phase=Failed` with `Reconciled=False`. The
operator ServiceAccount could not create `gitops-applicationset-controller`:

```
roles.rbac.authorization.k8s.io "gitops-applicationset-controller" is forbidden:
user "system:serviceaccount:gitops-operator:openshift-gitops-operator-controller-manager"
is attempting to grant RBAC permissions not currently held:
applicationsets, applicationsets/finalizers (all verbs)
applicationsets/status (get, patch, update)
coordination.k8s.io leases (delete, list, patch, watch)
extensions deployments (get, list, watch)
```

The ApplicationSet RBAC sits outside `CONTROLLER_CLUSTER_ROLE` and
`SERVER_CLUSTER_ROLE`, and `defaultClusterScopedRoleDisabled` does not reach the
cluster-scoped pair the operator creates in cluster-config mode. Pre-creating the
namespaced Role does not help: the operator always calls `Update`, and the RBAC
storage layer checks an update against the full rule set with no old-versus-new
diff (Kubernetes 1.36 `pkg/registry/rbac/role/policybased/storage.go`).

Resolution, now in the child bundle: a namespaced `Role`/`RoleBinding`
`openshift-gitops-operator-applicationset-grant` bound to the operator
ServiceAccount with the operator's own ApplicationSet policy, plus the
cluster-scoped `ClusterRole`/`ClusterRoleBinding`
`gitops-argocd-argocd-applicationset-controller` with the operator's cluster rule
list. No `escalate` verb, and the manager `bind` list still names exactly the two
ClusterRoles. Mechanism and residual are in
[`../GCP-1286_CSV_RBAC_REVIEW.md`](../GCP-1286_CSV_RBAC_REVIEW.md) §8.1.

Proven live on both clusters after the republish: all four objects exist with
`configmanagement.gke.io/managed: enabled` and source token `04f6e7d`, and the
ApplicationSet controller Deployment is `1/1`.

### 5.2 dex pull secret race on the region cluster

`gitops-dex-server` on the region cluster was `Init:ImagePullBackOff`, pulling
anonymously (`401`) from `registry.redhat.io`. The pod had no
`imagePullSecrets`; its ServiceAccount did. Timestamps explain it: the pod was
created at `15:55:56Z` and the propagated pull secret at `15:55:57Z`. The
operator copies the labeled pull secret from its own namespace into the Argo CD
namespace, and dex relies on ServiceAccount admission injection, so the first pod
missed the secret. The management cluster won the race and was unaffected.

Recovery: deleting the dex pod. The replacement came up `1/1 Running` with
`imagePullSecrets: [redhat-registry-pull-secret]`. This is a first-reconcile
ordering race, not a bundle defect; no ordering primitive can wait on a Secret
that the operator itself creates after the instance. It is recorded as a known
startup race with a one-step recovery.

### 5.3 MC Route/Scheme ordering (GCP-1441)

After the root ApplicationSet synced the management-cluster applications,
HyperShift's CRDs landed on the MC API server at `16:46:57Z`, including
`routes.route.openshift.io` at `16:47:00Z`. The GitOps manager had started at
`16:00:03Z`, before that CRD existed. The operator then began reconciling routes
and failed on every attempt:

```
no kind is registered for the type v1.Route in scheme "pkg/runtime/scheme.go:111"
```

`ArgoCD/gitops` stayed `phase=Failed` from `16:47:11Z` until the manager pod was
deleted at `17:08Z`. The replacement manager came up with the Route API present
and reported `phase=Available`, `Reconciled=True`; no Route object was created
because every route switch in the instance spec is disabled.

The released source registers the Route type only at manager startup:
`cmd/main.go` at `cf327714…` calls `routev1.AddToScheme` only when
`util.IsRouteAPIFound()`, and `InspectCluster` runs once. The 1.22.2 backport
(GITOPS-11466, PR #1354) makes Route detection independent of the Config API, so
a manager that starts after the CRD exists is fine. It does not cover a Route API
that appears after startup. On an MC that installs HyperShift through GitOps, the
manager always starts first, so this ordering is the normal case, not an edge
case.

Operational consequence: after the first application sync on a management
cluster, restart the GitOps manager once the Route CRD is present, or install the
Route CRD before the manager starts. Filed as GCP-1441, which also covers the
upstream issue for late CRD detection; GITOPS-11466 is closed for the
startup-detection case.

### 5.4 Fleet membership revision lag

See section 3. A successful Terraform apply reported the MC membership modified
while the live spec and state kept the old revision. Verification has to read the
Fleet membership spec, not the apply exit code, which is exactly why step 3 of
the runtime request asks for it.

### 5.5 Config Sync reconciler readiness on Autopilot

Every RootSync spec change rolls its reconciler Deployment. The `otel-agent`
container carries a fixed `10m` CPU limit from Config Sync's own manifest, so it
takes about 2.5 minutes to start serving its `:13133` health endpoint. Until then
the Deployment stays `Available: 0/1` and Config Sync holds the sync behind it
(`Reconciling=True:Deployment … Available: 0/1`). Observed on the region child,
the MC root and the MC child. It always resolved on its own; no pod was deleted
for this. Expect a few minutes per revision change when timing the run.

### 5.6 Restarts observed and explained

Region `gitops-server` restarted once. The previous container log at `16:24:21Z`
shows the settings watcher detecting a dex config change right after the
operator wrote `argocd-cm` with the instance URL, logging `dex config modified.
restarting`, emitting `GracefulRestartSignal`, and shutting down gracefully.
Argo CD then runs its in-process restart loop, took a second settings
notification while the cancelled RBAC informer was still unwinding, and ended
with `fatal ... error getting RBAC configmap "argocd-rbac-cm": ...
context canceled`. Kubernetes counts the non-zero exit as a restart. The
replacement has been serving since `16:24:22Z` with no further restarts. This is
Argo CD's restart-on-settings-change path (`server/server.go`), triggered by the
initial instance reconcile, not a crash loop.

Region operator manager restarted once at `17:10:38Z`, exit 1, with
`Error retrieving lease lock ... context deadline exceeded` and
`problem running manager {"error": "leader election lost"}` in the previous log.
The replacement came up and has been running without restarts; the instance
stayed `Available`. This was a transient API server timeout during the busy sync
window, and the operator re-reconciled normally after the restart.

The MC operator manager restart at `17:08Z` was deliberate (5.3). Every other
operand on both clusters shows zero restarts.

## 11. Teardown

The pair was destroyed on November 13, 2026 with the reviewed plan, not with a
fresh replan inside `teardown.sh`. The first reviewed plan reported `215 to
destroy` (`bbf3b1e1...`). After the partial apply, the remainder was re-planned
as `78 to destroy` (`6b0477bb...`) and the last eleven service-project
resources as `11 to destroy` (`5c3a8d25...` in the apply log).

Post-destroy state:

- `terraform state list` returns nothing.
- `dev-reg-us-c1-rfl1286m1111`, `dev-mgt-us-c1-rfl1286m1111` and
  `gcp-hcp-dev-svc-rfl1286m1111` all report `DELETE_REQUESTED`.
- The deployment folder `folders/1029606351992` reports `DELETE_REQUESTED`.
- The two delegation NS records for `rfl1286m1111` are gone from the commons
  zone. No shared project, zone, or folder outside the deployment was touched.
- `terraform/modules/region/cdn.tf` is restored with `prevent_destroy` back at
  line 49.

Blockers met during teardown, all resolved inside the deployment:

1. The GitOps operator restored the Argo CD operand deployments within seconds
   of the script scaling them down, and Argo CD then recreated the Gateways,
   HTTPRoutes, health check policies and backend policies. `teardown.sh` scales
   namespaces but never the operator that manages them, so the loop never
   converged. Scaling the operator to zero first fixed it.
2. The CNRM validating webhook Service had been deleted while its pods kept
   running. Every finalizer update then failed closed, and four IAM objects
   stayed behind. The cluster was going away, so the leftover validating
   webhook configurations were removed and the finalizers cleared directly.
3. The GMP StatefulSet recreated its PVC after the script deleted it, which
   aborted the script's 180 second verification. Scaling the StatefulSet to
   zero and deleting the PVC again fixed it.
4. `wait_for_resource_deletion` increments its counter once per loop instead of
   by elapsed time. When many resources are listed each iteration takes about
   thirty seconds, so the nominal 180 and 600 second limits become hours. With
   few resources it behaves as written, which is why the script aborted at 180
   iterations rather than 180 seconds.
5. The Fleet config-management feature and its two memberships had already been
   removed by the script's own Fleet disable, so their delete returned 404. They
   were removed from state.
6. The discovery bucket has versioning enabled and the bucket delete raced its
   own manifest object, so `force_destroy` blocked it. The orphaned object
   version was removed through the GCS JSON API and the bucket then deleted.

`gcloud storage` and `gsutil` are both unusable on this workstation (`ssl has
no attribute PROTOCOL_TLSv1`), so bucket inspection and the object delete went
through the JSON API.

Items 1 through 4 are repo defects in `teardown.sh` and apply to any pair torn
down with a running GitOps operator. They are filed as GCP-1440, which also
carries the Fleet 404 and versioned-bucket cases from items 5 and 6.
