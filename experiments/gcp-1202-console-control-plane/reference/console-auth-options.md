# Console Authentication Options for Control-Plane-Side Bridge

Authoritative analysis of authentication modes for the OpenShift console bridge when deployed on the HyperShift control-plane side for GCP HCP. This document covers the authentication mechanisms, OIDC requirements, client secret handling, session management, and Google OAuth setup considerations.

## Overview: Authentication Modes

The OpenShift console bridge supports exactly two production authentication modes, selected by the `--user-auth` flag:

| Mode | Cluster `Authentication.spec.type` | Client Secret Required? | Use Case |
|------|-----------------------------------|------------------------|----------|
| `openshift` (integrated OAuth) | `""` / `IntegratedOAuth` / `None` | Yes — auto-generated by console-operator | Standard OpenShift with integrated OAuth server |
| `oidc` (external OIDC) | `OIDC` | Yes — admin must manually provision | External identity provider (e.g., Google, Keycloak) |
| `disabled` | n/a | No | Dev/debug only — **not production-suitable** |

For GCP HCP, the **`oidc` mode** is the primary path, using Google as the external OIDC issuer.

## Integrated OpenShift OAuth (`openshift` mode)

### How It Works

- The console authenticates users through the integrated OpenShift OAuth server (`oauth-openshift` pod).
- Login flow: browser → console `/auth/login` → OAuth server → identity provider (HTPasswd, LDAP, GitHub, etc.) → OAuth server issues token → console validates token.
- The console-operator automatically creates an `OAuthClient` object and generates a 256-bit client secret.

### Requirements

1. A running integrated OAuth server with at least one configured identity provider in `OAuth.spec.identityProviders[]`.
2. `Authentication.spec.type` set to `""`, `IntegratedOAuth`, or `None`.
3. An `OAuthClient` CR named `console` — created automatically by console-operator.
4. A client secret — generated and managed automatically by console-operator in `Secret/console-oauth-config`.

### HyperShift Context

On HyperShift hosted clusters, the integrated OAuth server is **not present by default**. Enabling it is an explicit HostedCluster configuration choice. The PoC did not use this mode, because GCP HCP currently targets external OIDC.

**This is not settled, and it is the largest fork for console authentication.** There are parallel discussions about adopting the internal OpenShift OAuth server to support multiple and custom identity providers. If that happens, the console delegates login to `openshift-oauth` and never needs its own Google client — which removes the entire fleet-provisioning problem described below rather than solving it.

It also fits the control-plane-side topology particularly well: in HyperShift the OAuth server already runs control-plane-side and is already exposed at `oauth.<domain>`, on the same router and the same wildcard certificate as the console would be. Both ends of the login flow would sit on the management cluster, with no guest dependency.

Hence the spike's standing recommendation to keep the bridge's authentication **pluggable** rather than hard-wiring the OIDC path. Treat everything below as conditional on external OIDC remaining the model. See [`../open-questions.md`](../open-questions.md) §1.

## External OIDC (`oidc` mode)

### How It Works

- The bridge performs standard OIDC discovery against an external issuer (e.g., `https://accounts.google.com`).
- Login flow: browser → console `/auth/login` → external IdP authorization endpoint → user authenticates → IdP redirects to console with authorization code → bridge exchanges code for ID token → bridge validates token and creates session.
- Bridge implementation: `pkg/auth/oauth2/auth_oidc.go` uses `coreos/go-oidc` for discovery and `golang.org/x/oauth2` for the token exchange.

### Requirements

1. **External OIDC issuer** reachable from both the console pod and user browsers (e.g., Google, Keycloak, Entra ID).
2. **`ExternalOIDC` feature gate** enabled on the cluster.
3. **Registered OIDC client** on the external IdP with:
   - A `clientID`
   - A redirect URI: `https://console.<domain>/auth/callback`
   - **A client secret** (see below for why this is mandatory)
4. **Secret in `openshift-config` namespace** holding the client secret under the `clientSecret` key.
5. Optionally, a ConfigMap with the issuer's CA bundle if not publicly trusted.

### Client Secret is Effectively Mandatory

Although the `OIDCClientConfig.clientSecret` API field is documented as optional ("public clients do not require a client secret"), **the console bridge requires a client secret in practice**:

- console-operator's `oidcSetupController` marks the console `Degraded` with `OIDCClientMissingSecret` if `clientSecret` is unset and does not configure the bridge.
- The bridge itself requires `ClientSecret` or `ClientSecretFile` at flag-validation time for both `openshift` and `oidc` modes — there is no PKCE/public-client code path implemented.

**Why the console needs a confidential client:** The console bridge is a server-side web application that performs a confidential authorization code flow (code → token exchange with client secret). This is structurally different from public clients like the CLI (`oc`), which can use PKCE. The console must authenticate itself to the IdP during the token exchange, requiring a secret.

**Consequence:** Omitting the client secret results in:
- `Authentication.status.oidcClients[]` showing `Degraded: True, reason: OIDCClientMissingSecret`.
- Console ClusterOperator reporting Degraded.
- No functional browser login.

### Authentication Configuration Example

```yaml
apiVersion: config.openshift.io/v1
kind: Authentication
metadata:
  name: cluster
spec:
  type: OIDC
  oidcProviders:
  - name: google
    issuer:
      issuerURL: https://accounts.google.com
      audiences:
      - <console-client-id>.apps.googleusercontent.com
    claimMappings:
      username:
        claim: email
      groups:
        claim: hd
    oidcClients:
    - componentNamespace: openshift-console
      componentName: console
      clientID: <console-client-id>.apps.googleusercontent.com
      clientSecret:
        name: console-oidc-client-secret
      extraScopes:
      - email
      - profile
```

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: console-oidc-client-secret
  namespace: openshift-config
type: Opaque
stringData:
  clientSecret: <secret-from-google>
```

### Why OIDC Status Writes are Not Required for Login

The `Authentication.status.oidcClients[]` field is **status-only** and **not required** for the console login flow to work. The console-operator writes this status to indicate health, but the bridge only reads the spec fields:

- `oidcProviders[].issuer.issuerURL`
- `oidcProviders[].oidcClients[].clientID`
- `oidcProviders[].oidcClients[].clientSecret`

**Implication for GCP HCP:** The PoC hit an issue where `oidcProviders[].oidcClients[]` is not admissible in the guest `Authentication` CR because its CEL validation requires a matching `status.oidcClients` entry, which only a running guest console-operator writes. Since the console-operator runs control-plane-side (or is absent), nothing populates the guest status.

**Workaround:** The console client ID is added directly to the guest kube-apiserver OIDC **audiences** (not via `oidcClients[]`), and the client configuration is passed to the bridge via command-line flags. This bypasses the CEL validation and works for login. A control-plane-side owner of `status.oidcClients` is a future enhancement.

## Bridge Flags for OIDC Mode

The bridge requires the following flags to operate in OIDC mode:

```
-user-auth=oidc
-user-auth-oidc-issuer-url=https://accounts.google.com
-user-auth-oidc-client-id=<client-id>.apps.googleusercontent.com
-user-auth-oidc-client-secret-file=/var/oidc/clientSecret
-user-auth-oidc-token-scopes=email,profile
-cookie-encryption-key-file=/var/session/encryptionKey       # 32-byte AES key
-cookie-authentication-key-file=/var/session/authenticationKey  # 64-byte HMAC key
```

### Flag Details

- **`-user-auth-oidc-issuer-url`**: The OIDC issuer URL (e.g., `https://accounts.google.com`). The bridge performs discovery at startup against `<issuer>/.well-known/openid-configuration`.
- **`-user-auth-oidc-client-id`**: The OAuth client ID registered on the external IdP.
- **`-user-auth-oidc-client-secret-file`**: Path to a file containing the client secret. Alternatively, `-user-auth-oidc-client-secret` can pass the secret directly (less secure).
- **`-user-auth-oidc-token-scopes`**: Space or comma-separated list of OAuth scopes to request. **Required:** `email,profile` for GCP HCP because the cluster maps `username ← email`. Without these scopes, Google omits the `email` claim, causing the kube-apiserver to reject every request with `claim not present`.
- **`-cookie-encryption-key-file`**: 32-byte AES key for encrypting session cookies.
- **`-cookie-authentication-key-file`**: 64-byte HMAC key for signing session cookies.

The bridge builds the authorization request scope as `<token-scopes> + openid`, so `-user-auth-oidc-token-scopes=email,profile` results in `email profile openid`.

## Session Handling and Multi-Replica Deployment

### Per-Pod Session State

Under OIDC mode, the bridge keeps login state **per-pod in memory** and names its session cookie using the `POD_NAME` environment variable (injected via the Kubernetes downward API). Each replica has its own session cookie namespace.

**Challenge:** The HCP router is SNI passthrough and cannot perform cookie-based session affinity. Service `sessionAffinity: ClientIP` is ineffective because the router dials the Service fresh for each connection, and the source IP is always the router pod IP (not the end-user's IP).

### Cross-Pod Session Recovery via Refresh Tokens

The bridge can recover a session on a different pod **only** from a refresh-token cookie. The OIDC authentication path has no access-token recovery fallback (unlike the integrated OAuth path).

**Problem:** By default, the bridge does not request a refresh token during the OIDC login flow, causing an endless re-authentication loop when traffic shifts between replicas.

**Solution:** The bridge must request offline access during the OIDC authorization flow using the `access_type=offline` and `prompt=consent` parameters. This causes Google (and compatible IdPs) to issue a refresh token. When a request lands on a different pod, that pod silently performs a back-channel token refresh using the refresh token, rebuilding the session without user interaction.

**Implementation:** PR openshift/console#17185 adds these parameters to the OIDC authorization URL. Note that Google does **not** honor the standard `offline_access` scope — the `access_type=offline` query parameter is required instead.

### Multi-Replica Verification

With the refresh-token enhancement, multi-replica deployments (`replicas: 2`) work correctly:
- Deleting the pod holding a user's session does not force a re-login.
- Traffic can shift between replicas transparently.
- No sticky routing or session affinity is needed.

## Google OAuth Client Setup

### Client Type: Web Application

The console requires a **Web application** OAuth client on Google Cloud:

1. Navigate to **Google Cloud Console → APIs & Services → OAuth consent screen**.
2. Configure the consent screen (Internal or External) with scopes: `openid`, `email`, `profile`.
3. Navigate to **Credentials → Create Credentials → OAuth client ID**.
4. Select **Application type: Web application**.
5. Add the authorized redirect URI:
   ```
   https://console.<domain>/auth/callback
   ```
   The path `/auth/callback` is fixed by the bridge (`AuthLoginCallbackEndpoint`).
6. Create the client and copy the **Client ID** and **Client secret**.

### Why the Console Needs Its Own Google Client

- The guest kube-apiserver uses Google's shared public client ID (`32555940559.apps.googleusercontent.com`) as an OIDC **audience** for token validation. This client is public (no secret) and supports only loopback/out-of-band redirects.
- The console bridge is a **confidential web application** that requires a registered web redirect URI (`https://console.<domain>/auth/callback`) and performs a code → token exchange with a client secret.
- These are structurally incompatible client types — the console cannot reuse the kube-apiserver's public client.

**Consequence:** A dedicated Google Web application client is mandatory for console login.

### Constraints That Complicate Fleet Provisioning

Google imposes hard constraints on OAuth client creation:

- **No API/CLI to create Web OAuth clients** — creation is Console-UI-only. Neither `gcloud` nor Terraform can automate this.
- **No wildcard redirect URIs** — each redirect URI must be an exact HTTPS match.
- Client secret is shown **once** at creation.

**Fleet Impact:** Creating a hosted cluster **must not require a manual Google step**. Any design where Google *must be changed during* cluster creation violates this principle.

Note the distinction, which matters: the constraint is on the *creation flow*, not on Google ever seeing a per-cluster redirect URI. A redirect URI is a mutable property of a Google client, so it can be added after the cluster exists without blocking creation. ARO HCP relies on exactly that — it registers an exact per-cluster callback derived from the created cluster's console URL, rather than a wildcard, even though Entra would permit wildcards for org-only tenants.

### Client Model Options

Two shapes, and they answer different questions.

**Day-2 customer-supplied client (designed, with an ARO precedent).** The customer brings a Google client that pre-exists the cluster, so its client ID can be set in `HostedCluster.spec` at creation — in both `issuer.audiences` and `oidcClients[]`. After the cluster exists, the customer adds the redirect URI to that client and creates the client secret guest-side. Nothing mutates the HostedCluster after creation. This removes the ordering impossibility but keeps one manual Google step, moved out of the creation path and owned by the customer.

**Zero-touch provisioning (unbuilt).** A state-based redirect broker — one fleet-fixed Google redirect URI with the target cluster encoded in the OAuth `state` parameter — or an intermediate IdP supporting dynamic client registration. Either removes the manual Google step entirely. Both need new fleet auth infrastructure, and the broker additionally needs upstream bridge support it does not have today.

Full design, code changes and the open product decision: [`../open-questions.md`](../open-questions.md) §1.

### Both Fields Are Required

`issuer.audiences` and `oidcClients[].clientID` are independent; neither is derived from the other. The KAS authenticator's audience list is built solely from `issuer.audiences`, in HyperShift and in standalone OpenShift alike (two independent implementations with identical logic; no shared library-go helper). A client ID listed only under `oidcClients` will not be accepted as a token audience.

The official OpenShift external-auth documentation reflects this, listing each client ID twice:

```yaml
issuer:
  audiences: [console-test, oc-cli-test]
oidcClients:
- clientID: oc-cli-test
  componentName: cli
- clientID: console-test
  clientSecret: { name: console-secret }
  componentName: console
```

`clientSecret` appears only on the console entry — the CLI client is public, the console client confidential.

## Observed Symptom: Benign Login-Role Metric Error

Under pure OIDC mode (no integrated OAuth server), a harmless error appears in the bridge logs:

```
auth.metrics isKubeAdmin: users.user.openshift.io API not available
```

This occurs because the bridge's login metrics code queries the OpenShift User API (`users.user.openshift.io`) to determine if the user is `kube:admin`. Under pure Google OIDC, this API does not exist.

**Impact:** None. The error is logged but does not affect login functionality. It is a known upstream limitation acknowledged in the code (`// FIXME`).

## Dev/Debug Mode (`disabled`)

The `--user-auth=disabled` mode bypasses all authentication:

- With no `--k8s-auth-bearer-token`: every request is treated as authenticated with no identity check. Logged as a loud warning.
- With `--k8s-auth-bearer-token=<token>`: every request is authenticated as a single static user/token.

**This mode is not wired to the `Authentication` CR and is not production-suitable.** It exists only for local development and throwaway environments.

## Summary Decision Table

| Question | `openshift` | `oidc` | `disabled` |
|----------|-------------|--------|------------|
| Cluster `Authentication.spec.type` | `""` / `IntegratedOAuth` / `None` | `OIDC` | n/a |
| Feature gate needed | None | `ExternalOIDC` | None |
| Client secret needed | Yes — auto-generated | Yes — admin must create | No |
| Identity provider config | `OAuth.spec.identityProviders[]` | External IdP | None |
| Admin action to enable | Configure identity providers | Enable feature gate, register client+secret, add `oidcClients[]` entry | Set flag only |
| Production-suitable | Yes | Yes | **No** |
| GCP HCP use case | Not applicable (no OAuth server) | **Primary mode** | Dev only |
