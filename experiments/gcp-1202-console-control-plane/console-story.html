GCP-1202 · HyperShift on GCP

Console on the control plane

00 · OVERVIEW

The console is the last guest-side dependency

Today the console runs as a Deployment on the guest workers, behind the default ingress. That is what makes it unavailable on a cluster with zero workers, and what exposes it to customer-side ingress, DNS and certificate changes.

Move it to the HostedControlPlane namespace and it becomes another control-plane operand: reached through the same exposure as the API, served by the platform certificate, and independent of the customer's ingress.

01 · CLASSIC

The console lives on the workers

A guest Deployment in openshift-console, two replicas, reconciled by the console-operator. Workers are a hard dependency: no workers, no console.

Everything it talks to is either on the same pod network — Thanos, Alertmanager, plugin backends — or reached through the cluster's API endpoint. In this model the console is a guest workload with a guest URL.

02 · CLASSIC

Entry through the default ingress

Browser → default ingress controller → console. The ingress capability is mandatory: with no router there is no console Route, and without the *.apps.<domain> record in the customer's DNS there is no hostname to reach. The ingress operator publishes that zone.

In a private cluster the ingress load balancer is customer-side and internal, so the browser must already be inside the VPC.

03 · CLASSIC

The certificate crosses two projects

cert-manager runs on the management cluster and cannot write the customer's ingress zone. A DNS-01 CNAME delegates the ACME challenge from *.apps to the central zone that hosts the API record, so cert-manager can solve it. That delegation is a day-0 requirement.

The issued certificate lands in the guest as a secret — visible, and modifiable, on the customer side. The console-operator copies it onto the Route (spec.tls, reencrypt), the router terminates the browser TLS and re-encrypts to the console Service, and the backend certificate is issued automatically by service-ca.

04 · CLASSIC

API through PSC, plugins direct

The guest kube-apiserver runs in the HCP namespace, so nodes and pods — including the console — always reach it through the PSC endpoint, the private LB and the HCP router. GCP HCP uses PublicAndPrivate, never the full Public mode, so this is true in every cluster mode and lets a cluster move to Private without changing the path.

Monitoring and plugin backends are different: Thanos, Alertmanager and plugin Services are ClusterIPs in the guest pod network. The console reaches them directly, with no tunnel and no proxy.

05 · TRANSITION

The move

The console becomes a Deployment in the HostedControlPlane namespace on the management cluster. Two things leave the path: the guest ingress and the *.apps record.

The hostname changes from console-openshift-console.apps.<domain> to console.<domain>, a sibling of the API. Bookmarks, runbooks and the customer's IdP redirect URI follow it.

06 · CONTROL PLANE

Entry alongside the API

Same exposure machinery as the API: PSC endpoint and a control-plane-side private LB for private clusters, a control-plane-side public LB for public clusters. No customer ingress, no customer load balancer.

The HCP router is SNI passthrough. It forwards console.<domain> to the console Service without terminating TLS, so the certificate is served by the pod itself — the platform wildcard that already covers the API, mounted from external-api-cert.

07 · CONTROL PLANE

The API is in the same namespace

The guest kube-apiserver is a ClusterIP Service beside the console: kube-apiserver.<hcp-namespace>.svc:6443. No PSC, no router, no tunnel; NO_PROXY keeps this path out of the proxy.

The console trusts the control-plane root CA for that hop, and needs a guest service-account identity for its own backend calls — dashboards, plugin metrics. The PoC mints and refreshes one with a token-minter sidecar.

08 · CONTROL PLANE

Plugins and metrics take the tunnel

Thanos, Alertmanager and plugin backends stay on the workers' pod network. The console reaches them through a socks5 sidecar → konnectivity-server → reverse tunnel → guest agent.

The agent dials out; the control plane never initiates into the customer VPC. Names resolve through the guest KAS ClusterIP, so no DNS is involved. The console trusts the guest service-ca for these backends, and the tunnel itself is mTLS. The pod terminal does not use it — that rides the direct KAS path.

09 · AUTH

Same intent, different plumbing

The cluster authenticates with external OIDC today, and the console does too. On the worker side the component operator writes the console's client entry into the guest API, and the authentication operator feeds the accepted client ID to the KAS.

In the split topology there is no component operator in the guest. The PoC mounted the client secret into the pod and added the client ID to the KAS audiences by hand. What is not automated is the registration itself — something has to write the console's client into the guest and get it accepted. The KAS mechanics are the same.

Moving to the integrated OAuth server is under discussion; it would replace the client-ID list with OAuthClient registration. Either way the console's public URL changes, so customer-side configuration that names it — the IdP redirect URI today — has to be updated.

10 · DOWNLOADS

Downloads follows the console

Core downloads move with the console: a separate Deployment in the HCP namespace with an oauth-proxy sidecar — the SNI-passthrough router cannot terminate the Route TLS — on downloads.<domain> and the same platform wildcard.

Additional download extensions can stay on the workers. Those are the exception: they keep an ingress dependency of their own.

11 · CUSTOM NAME

A customer hostname and its certificate

Customers ask for the console on their own name — console.acmecorp.com — with their own certificate. We keep the standard configuration location: the guest cluster's Ingress.spec.componentRoutes[], a hostname and a servingCertKeyPairSecret in openshift-config.

The certificate has to move. Upstream the ingress router terminates it; the HCP router passes SNI through and terminates nothing, so the secret must be synced into the HCP namespace and served by the console. The console-operator — adapted for this control-plane-side deployment, or replaced by an equivalent component — reads the hostname and the secret, configures the console with them, and creates the Route that gives the router its SNI match.

Untested, but feasible in principle. Open: how the console picks a certificate per name, and whether the custom name replaces console.<domain> or serves beside it.

12 · THE TRADE

What changes, and what does not

Unlocked: zero-worker clusters; no customer ingress, load balancer, DNS record or certificate on the console's path; the console under the same SLO ownership as the API.

Unchanged: the console binary, its UI, the plugin model, and RBAC and identity semantics.

Open: the auth model (external OIDC or the OAuth server), session stickiness across console replicas (openshift/console#17420, under review), and whether the console-operator evolves to a dual-API design or is replaced by a new operator using the existing one as a library. The runtime path is proven; the remaining decisions are product and upstream consensus.
